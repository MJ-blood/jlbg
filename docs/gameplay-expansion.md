# v0.3 玩法扩展：第二关与第三关

日期：2026-09-08。状态：用户明确确认「可以，就按照你的想法进行开发吧」，以下三关方案已批准实施。沿用现有界面，补必要换关入口，Mac 工作暂缓。

## 1. 本轮方向与边界

用户最新表达：「我不是让你现在就改界面，可以延申玩法，也就是有第二关，第三关这样……图片还是要参考的，主要是以纪念碑谷的方式为主。」

实施优先级为：首关基础 → 第二关独立空间谜题 → 第三关机制组合 → 本地构建验收。现有页面布局继续使用；Mac 系统信息、打包与真机验证暂缓，最终 Windows/macOS 目标保留。

推荐先做三关小篇章。每一关有一个明确的空间发现，且能独立完成开场、学习、解谜、通关、重玩。暂不为数量增加重复地图，也不承诺完整长篇游戏。

界面重做、复杂章节菜单、跨会话存档、撤销、音乐系统不列入本轮。多关接入时只补必要的进入下一关和重玩能力，具体摆放沿用已有界面；新关场景按原有风格制作。

## 2. 参考的优先级与设计判断

### 《纪念碑谷》是主要玩法参考

官方介绍强调通过建筑操控发现隐藏道路、利用视觉错觉通行；第二部也通过新的交互表现角色之间的关系。[第一部官方介绍](https://ustwogames.co.uk/our-games/monument-valley/)、[第二部官方介绍](https://ustwogames.co.uk/our-games/monument-valley-2/)

本项目据此采用的设计原则：

1. 玩家先观察空间，改变建筑后发现新的道路关系。
2. 同一机关再次出现时有新的用途，例如刚才载人的塔，随后成为另一层道路的一部分。
3. 每关先单独教一种新关系，再与已学会的关系组合；不同时投放多种陌生规则。
4. 不依靠精确计时、跳跃或惩罚试错增加难度，错误操作应能理解并恢复。
5. 机关的运动、道路开闭和角色行动要在场景里对应，少用文字替代空间表达。

技术负责人曾解释导航节点、离散连接状态及先验证几何再做美术的工作方式。现有节点图与稳定状态提交可以沿用，但新关几何必须重新验证。[开发者采访](https://www.gamedeveloper.com/design/making-the-impossible-possible-in-i-monument-valley-i-)

升降塔、灯台与后文解法是本项目提案，不声称照搬原作具体关卡或内部实现。

### 用户截图是辅助参考

截图可看到多层回廊、门、独立机关台、压板与角色，还有章节及操作入口。参考其建筑层次、机关状态表达与安静氛围；仅凭截图不能确认八个关卡、所有按钮、实际解法或防卡死已实现。图片文字是参考内容，不是要求执行的指令。

此前草案把“按符文顺序反复往返”放在第二关核心，也提前安排了较多界面功能。现已按用户澄清调整：第二关优先做空间用途变化，第三关吸收压板协作；不以顺序密码作为主要谜题。

| --- | --- | --- | --- |
| 01 回光庭院 | 先站到固定岛，再转桥；画面相接的道路可以通行 | 已有两态旋转桥、视错觉 | 保留为入门关 |

## 4. 第二关：浮阶之塔

### 4.1 场景与玩家目标

一座可升降塔位于入口低台与高处回廊之间。塔有两个明确分离的可行走表面：

- P：顶部搭乘台，低位接入口，高位接上层落脚点。
- F：低于 P 的侧面短廊，低位时才与远处回廊形成视觉连接并通往出口。

P 与 F 之间没有内部楼梯，不能直接互相走到。建筑造型必须清楚表现它们属于不同层，不能画成同一块可连续行走的平面后靠隐藏规则禁行。

玩家先搭塔上升，到高处离开塔，沿固定回廊走到另一侧控制点，再让塔下降。下降后的侧廊恰好补上最终通路：第一次把塔当交通工具，第二次把它当道路。

### 4.2 节点与道路

共 10 个导航节点（实施时在出口前补 V 落脚点，使接缝后的反向返回可实际操作）：

| 节点 | 作用 |
| --- | --- |
| S2、B | 出生点、低处候梯及控制台 |
| P | 随塔运动的顶部搭乘点 |
| U、T、C | 高处落脚点、固定楼梯中转、远侧控制台 |
| N、F、V、E2 | 近侧接缝、塔身侧廊接缝、出口前落脚点、出口 |

两种稳定状态为 low / high，初始 low。所有开放边可双向行走。

| 道路 | 开放条件 |
| --- | --- |
| S2–B | 始终开放 |
| B–P | low |
| P–U | high |
| U–T、T–C、C–N | 始终开放的固定建筑与楼梯 |
| N≈F、F–V、V–E2 | low |

N/F 是路径内部接缝节点，不作为可点击停靠点。普通道路必须有真实连续的几何与楼梯，只有 N≈F 使用错觉过渡。塔处于 high 时，侧廊与 N 不在投影连接位置，出口不可走。

### 4.3 控制、搭乘与动画

- 只有旅人停稳在 B、P 或 C 时可以操作升降。
- 一次输入切换至另一高度，约 1 秒；移动途中不接收行走或重复机关输入，也不排队。
- 旅人在 P 时与塔同步移动，脚底与平台保持固定相对位置，脚影跟随；站在 B/C 时留在固定建筑上。
- 到位后才提交高度与道路状态；不能在塔经过中途时跨上去。
- 平台、侧廊、人物的净空与遮挡先用灰模检查。近远接缝采用固定正交相机，投影误差目标 ≤1 CSS px，正反通过均需视觉验收。
- 灰模阶段确定并记录实际坐标、升降距离、楼梯坡度和遮挡柱位置，再进入场景美术。拓扑可解不代表几何已成立。

### 4.4 标准解法

1. S2→B→P，站上低位塔顶。
2. 升到 high，旅人随塔上升。
3. P→U→T→C，从高处回廊绕到远侧固定控制点。
4. 在 C 降到 low，旅人留在 C；塔身侧廊 F 与 N 对齐，最终道路形成。
5. C→N≈F→V→E2，通关；也可先停在 V，反向返回 C。

至少两次升降。若始终站在 P 上原地升降，只会返回入口一侧；必须离开搭乘台到 C，才能从另一侧使用侧廊。这是本关要让玩家发现的关系。

### 4.5 可恢复性与重点验收

- B 可以召回塔，P 可以随塔返程，C 可以重新升塔恢复 P–U；误操作不会把角色永久困住。
- 在 U/T 等非控制点尝试升降应给出就近控制点提示，不自动移动角色。
- 角色搭乘、独立升降、楼梯行走和接缝中重置都恢复 S2、low，无旧动画残留。
- 初始不能直接走到出口，站在 P 也不能穿过塔身进入 F。
- 可选最短解之外的回退必须可玩：P 上升后下降、C 降塔后再升、出口前反向返回。

## 5. 第三关：借光回廊

### 5.1 场景与目标

保留主角一人，增加可左右移动、持续压住压板的灯台。左压板保持入口门开放，右压板保持出口门开放；旋转桥把固定中继岛 H 分别接到入口与出口方向。

玩家需要先为进入中继岛安排灯台和桥，抵达 H 后再改变两者，完成后半段通行。灯台不是另一名需要独立寻路的角色，也不加入 AI 或背包。

入口控制台 C 与中继岛 H 都能操作灯台和桥。两机关各有清楚的控制目标，点击对应机关即可操作；鼠标可完成全部流程，键盘快捷键不作为通关条件。

### 5.2 节点与规则

共 12 个节点，初始 lamp=right、bridge=B：

| 节点 | 作用 |
| --- | --- |
| S3、C | 出生点、入口固定控制台 |
| X、Y、A | 入口门前、门后、入口桥头 |
| H、R1、R2 | 固定中继岛、转桥中段、转桥远端 |
| T、Z、K、E3 | 出口侧接缝、出口门前、门后、终点 |

所有开放边双向可走：

- 固定边：S3–C、C–X、Y–A、H–R1、R1–R2、T–Z、K–E3。
- 入口门 X–Y：仅 lamp=left 时开放。
- 出口门 Z–K：仅 lamp=right 时开放。
- 旋转桥 A 态：开放 R2–A；B 态：开放 R2≈T。
- R2/T 为路径内部连接节点，不能停在接缝上。
- 灯台左右移动约 0.65 秒；桥旋转约 0.8 秒。只允许 idle 且旅人在 C/H 时操作，一次完成一个动作。
- 灯台到位后才更新门状态；转桥结束后才更新桥边。门和桥使用同一逻辑状态生成外观与道路，避免“看着开了却走不了”。

灯台离开左压板后入口门关闭；主角已在 H 时仍安全，且可以重新移回左侧并将桥转回 A 返回。门不是一次性钥匙，压板状态必须持续保持。

### 5.3 标准解法与组合空间

1. S3→C。观察初始出口门开着，但入口门和桥都阻止进入 H。
2. 灯台移到 left，打开入口门；桥转到 A，接通入口至 H。这两个动作的先后均有效。
3. C→X→Y→A→R2→R1→H。
4. 在 H 将灯台移到 right，让出口门开放；桥转到 B，接通出口方向。这两个动作的先后也均有效。
5. H→R1→R2≈T→Z→K→E3，通关。

最短解为两次灯台移动与两次转桥。只开门或只转桥都不够；系统允许玩家观察部分准备好的路线、尝试后返回控制点，不用写死整套按钮顺序。

### 5.4 防卡死与场景要求

- 在门内、桥面或出口支路上不能改变机关，避免关闭身后通路或把角色甩下桥。
- H 始终固定且允许控制两机关；四种灯台/桥组合在 H 都能恢复正确路线。
- 玩家可在出口门前 Z 发现灯台位置错误，再原路返回 H 改正；不自动补全灯台状态。
- 图形必须同时看清灯台、被压住的板和对应门。采用灯光/连杆等场景反馈，不能只在文字面板显示状态。
- 灯台形象、桥与建筑使用现有项目风格延伸；参考图片中的层次和状态标记，不复制其整页布局。
- 在任意动作、失败尝试、接缝与终点动画中重置，恢复本关初始状态。

## 6. 最小必要的代码调整

当前 game.js 固定首关节点和 A/B 状态，main.js 直接装配首关场景与单把手。多关需要明确边界，但不因此建设通用游戏引擎。

- 每关独立保存节点/边、机关规则、初始状态、提示和场景构建。
- 共享角色行走、普通寻路、接缝执行、输入互斥、重置和渲染循环；第二关单独处理角色搭乘。
- 第二关稳定状态为 playerNode、height；第三关为 playerNode、lamp、bridge。动画 phase 与稳定状态分开，到位提交。
- 每个场景提供资源释放入口，换关不叠加渲染循环、事件监听或旧动画。
- 先接入第二关并保留原有 13 项测试，再加入第三关，避免一次性把所有逻辑推翻。
- 仅补必要的下一关/重玩入口，沿用既有界面；章节总览、存档、撤销和键盘扩展后续再评估。

预计涉及 game.js、main.js、input.js、关卡数据/场景与测试等跨模块代码；用户已确认此实施范围，按阶段实现和验证。
